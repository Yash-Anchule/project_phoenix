# Important Pydantic / FastAPI Validation Lesson

I tested:

```json
{
  "amount": 0,
  "category": "restaurants",
  "spent_at": "2026-10-05T09:31:12.359Z"
}
```

Pydantic rejected `"restaurants"` because the valid literal is:

```text
restaurant
```

FastAPI returned a validation error containing:

```text
type: literal_error
loc: ["body", "category"]
```

Meaning:

- The problem is a literal validation error.
- The error is inside the request body.
- Specifically, the `category` field is invalid.

# Why try/except ValidationError Did Not Work

My endpoint was:

```python
@app.post("/add_test")
def add_expense(data: ExpensePydantic, db=Depends(get_db)):
    try:
        expense = Expenses(
            amount=data.amount,
            category=data.category,
            spent_at=data.spent_at
        )

        db.add(expense)
        db.commit()

        return expense

    except ValidationError as e:
        print(e.errors())
        return e.errors()
```

This did NOT catch the invalid `"restaurants"` request.

Reason:

**FastAPI validates the request body before entering the endpoint function.**

Flow:

```text
HTTP request
    ↓
FastAPI
    ↓
Pydantic validation
    ↓
❌ validation fails
    ↓
RequestValidationError
    ↓
Endpoint never executes
```

Therefore the `try/except` inside the endpoint never gets a chance to run.

# RequestValidationError Handler

I also added:

```python
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=422,
        content={
            "detail": exc.errors(),
            "body": exc.body
        },
    )
```

This caused Postman to show both:

```text
detail
body
```

because we explicitly returned both.

`exc.errors()` contains the validation errors.

`exc.body` contains the request that caused the error.

We also discussed that adding:

```python
print("Validation error:", exc.errors())
```

inside this exception handler lets us log the error in the Uvicorn terminal.

Important distinction:

```text
Pydantic ValidationError
→ when manually constructing a Pydantic model

FastAPI RequestValidationError
→ when incoming HTTP request data fails FastAPI/Pydantic validation
  before the endpoint executes
```

# Budget Design Decision

We decided NOT to create separate budgets for each expense category.

Instead, Phoenix will have **one overall monthly spending limit**.

Example:

```text
Monthly Budget = ₹30,000
```

Expenses might be:

```text
Groceries       ₹5,000
Restaurant      ₹3,000
Shopping        ₹4,000
Travel          ₹2,000
Entertainment   ₹1,000
...
```

Categories are used for analysis, not separate budgets.

---

# Important Budget Data Principle

We should NOT continuously subtract expenses from the budget row.

For example, avoid:

```text
Budget starts at ₹30,000
→ expense ₹500
→ budget becomes ₹29,500
→ expense ₹1,000
→ budget becomes ₹28,500
```

Instead:

```text
Budget table stores:
monthly_limit = ₹30,000

Expense table stores:
all actual expenses
```

Then derive:

```text
total_spent = SUM(expenses for current month)

remaining = monthly_limit - total_spent
```

This keeps the database consistent.

If an expense is deleted or updated, the spending total automatically changes based on actual expense records.

# Backend vs Agent Responsibilities

We discussed that the LangGraph agent should NOT directly interact with PostgreSQL.

The backend should own the database and business rules.

The preferred architecture is:

```text
User
  ↓
LangGraph
  ↓
Budget Agent
  ↓
Tool
  ↓
FastAPI
  ↓
Business Logic
  ↓
SQLAlchemy
  ↓
PostgreSQL
```

The LLM/agent decides:

> What does the user want?

The backend decides:

> What is actually true and what should happen?

For example, the LLM should NOT be responsible for calculating:

```text
₹30,000 - ₹22,400
```

The backend should calculate:

```text
remaining = monthly_limit - total_spent
```

because this is deterministic business logic.

The agent then explains the structured result naturally to the user.
